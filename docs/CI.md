# Continuous integration and regression policy

Every push to `main` and every pull request runs native Linux arm64 (`ubuntu-24.04-arm`), Linux x86-64 (`ubuntu-24.04`) and macOS arm64 (`macos-15`) checks. Merge groups and manual runs use the same workflow. The final **CI** check succeeds only when every native job and the issue-policy job succeed; skipped, cancelled and failed dependencies cannot produce a green gate. Main requires this GitHub Actions check and an up-to-date PR branch, including for administrators.

## What is tested

- Clean build from the committed seed and two byte-identical self-hosted compiler rebuilds.
- Every `tests/v2/*.tin`, including negative compilation tests and their exact diagnostics. Missing expected output, compiler crashes, process crashes, nonzero exit and timeouts fail. Each run uses fresh executable paths. Diagnostic codes (`diagnostics_check.py`, run by `tools/v2test.sh`): every code the compiler prints is documented in `docs/ERRORS.md` under the same name, every documented code is printed or retired, the compiler prints no error without a code, every line of the `.err` files and of the exact compile-phase regression contracts carries a documented code, and each documented example compiles to exactly the diagnostic the page shows. `tests/v2/*_asm.tin` files are compiled with `-S` instead and their listing matched against the ordered `CHECK:`/`CHECK-NOT:` lines in `*_asm.check` (the CPU's section), so a codegen change that loses a direct call, or turns it into an indirect one, fails.
- Docs (`docs_check.py`, Tin 1 #227): every fenced block in README.md and docs/ names its language, Tin code is fenced `tin`, no Tin code in the docs (blocks and inline code) or in `examples/` uses a form edition 1 removed, and every `tin` block of README.md and docs/ compiles with `-edition 1` (a block marked `error` must fail; docs/ERRORS.md examples are compiled by `diagnostics_check.py`). The block conventions (`body`, `file=NAME`, hidden `tin-prelude` comments) are in the script's header.
- Exact number conversion: a generated Go `strconv`/`fmt` corpus and pinned parse-number-fxx hard cases check float bits, faults, ties, subnormals, long inputs, precision and f32/format flags on all three native targets (`number_check.py`).
- Memory primitives (`memory_check.py`): Go twins check every alignment, overlap, zeroing, reallocation, guard-page boundaries and 1000 cross-core returns. Deterministic failure injection checks 46 allocation/mapping failures, including startup and later allocations (#178).
- Task memory (`task_memory_check.py`): 300 concurrent heavy requests dirty pool and deep stack pages; after release, the cache holds at most 64 tasks and Linux RSS returns to within 32 MiB of baseline (#177). macOS checks task reuse and cache invariants.
- Arenas (`arena_check.py`, Tin 1 #236, edition 1 fixture `arenas.tin`): a batch loop that writes 8 MB per step in an arena keeps its peak RSS flat from 10 to 200 steps on Linux, while the same loop without arenas (the control) grows by more than 150 MiB; 40 concurrent requests on one core, each running 8 arenas that wait inside them, all get their own values, and RSS does not grow across rounds. The language rules, copies, faults, panics, limits and pool sharing with scope children are in `tests/edition1/run/arenas.tin`, `arena_bad.tin` and `arena_value_bad.tin`.
- Replay tapes (`replay_check.py`, Tin 1 #241, `notes/interface_replay.md`): `rt_effect` records results and faults; a replaying tape serves them without running the live call, keeps fault identity (`fault.Is` on a recorded deadline), stops at the first divergence and keeps it, and calls kinds listed as live for real. Capsules: tapes a fixture records are written by `lib/replay` and opened in the check with Python's `hmac` (section 6): kept on a 5xx, a panic or a sample; secret headers and keys as handles and no secret text anywhere in the file; a wrong key or any changed byte fails the tag; the spool bound deletes the oldest capsules, at start and per core. Recording in anvil: a fixture server keeps the capsules of failed, panicked (with the message) and sampled requests, including one that waited, with the request as received (secret headers as handles) and its effects in order; with recording off or a malformed key nothing is written. Clients: one task's `tide`, `dice`, `seal`, `wire` (HTTP, dial, read, write) and `redis` calls against live local servers are recorded in order (secret headers as handles, no password on the tape); the same code replayed from the tape gets identical values with no connection made, and a changed Redis key is a divergence. The same for `mysql` and `postgres` (statements and transactions, against the fake servers of their checks), `websocket` (dial, write, read) and `quarry` (files): recorded in order with no database password on the tape, replayed with no connection made and no file touched. Replay mode (#242): capsules built in the check with Python's `hmac` (the documented envelope) replay through a checkout fixture: a recorded 500 and a recorded deadline without a live call, a changed call order reported as a divergence (exit 3), unserved effects, `--live`, a handler that waits or panics, unreadable capsules (exit 4), and `tin replay`'s options. Secret query values (`query.Hidden`, edition 1 fixture `replay_secret.tin`): sent to Redis and MySQL as themselves while the tape's keys hold their handles, and the replay matches. The checkout example (`examples/checkout.tin`, #242): a real 500, recorded against a local Redis and a declining payment service, replays through `tin replay` with both of them gone and answers the same; another payment service URL is a divergence (exit 3). Replaying computes secret handles with the recording's key, so keys that hold secrets still match.
- Scheduling replay (`sched_check.py`, Tin 1 #243, edition 1 fixture `sched.tin`): a select on a recording tape appends its winning arm (`sched.select@1`, keyed by file and line); replaying, it takes the recorded arm under the live timing that would make the other arm win, 20 times each way, and 30 recordings of a select racing a timer each replay their branch under both timings (the fixture counts branches, it never times them); a select left by its boundary's deadline records the arm count and its replay waits for the boundary too; a select at another site diverges. A request's tasks resume in the recorded order (`sched.resume@1`) when their waits are swapped; children whose effects complete in another order than issued get their results in the recorded order; a replay in which no task can take the next record diverges instead of hanging. Cancels are recorded with their boundary, task and reason (`sched.cancel@1`); a recorded 5 ms deadline replays under a 10 s one, and a race that beat a 500 ms deadline replays its branch under a 1 ms one: deadlines come from the tape, not the clock. End to end (edition 1 fixture `sched_serve.tin`): anvil records 32 requests whose select races a timer (`TIN_REPLAY_SAMPLE=1`), and `tin replay` replays each capsule under the live timing that makes each side win: every run takes the recorded branch, exits 0 and serves the whole capsule.
- Remaining helpers (`helpers_check.py`): exact errno messages, 2010 UTC/calendar values against Go and the former C output, hostname, PTYs/pipes/files, Linux affinity/page size and linker-symbol boundaries. `compiler_paths_check.py` checks copied installations, spaces/Unicode, symlink traversal and missing paths against Go/C.
- Linux DNS (`dns_check.py`): fake UDP/TCP servers check hosts precedence, A/AAAA and IPv6 sockets, CNAMEs, malformed compression, wrong IDs, truncation/TCP fragments, NXDOMAIN, search/ndots, rotation/retries/timeouts, concurrent request deadlines and memory stability over 1000 lookups.
- Memory regressions: bounds panics, allocation size overflow and negative lengths, large first allocations, single evaluation of allocation lengths, read-only and region checking through indirect calls, nested zero values, deep `keep` ownership and 200 request-pool reset/reuse cycles.
- Linux HTTP framing/conformance, stable RSS over two million requests after warmup, and graceful shutdown. Throughput is reported, never used as a performance threshold.
- Linux syscall ABI (`syscall_check.py`): kernel errors, mappings, poll, stat fields, 5004 long/linked directory entries with refills and forced unknown types, returning signal handlers on an alternate stack, independent core errors, and ELF assertions excluding libc syscall imports.
- Linux threads (`thread_check.py`): 208 cores started with the raw `clone` leaf return one after another; each has its own signal stack, inherits the blocked SIGTERM and keeps its own errors, and its stack and alternate stack are unmapped once the kernel clears its tid (no records, mappings or threads left). A stack overflow on a core thread is reported and exits 2.
- Static executables (`static_check.py`): the ELF writers emit an image with no PT_INTERP and no PT_DYNAMIC for both Linux targets when a program imports nothing; its Tin `_start` passes argc, argv and envp from the initial stack, and the binary runs in an empty root directory (chroot, when the runner allows it).
- Request tasks (`task_check.py`): waits on one core overlap, fast requests stay fast behind waiting ones (timers, proxied `wire` calls, helper-thread file I/O), deadlines give 504, refused upstreams 502, and pipelined responses keep their order.
- Router (`router_check.py`, server `tools/ci/fixtures/router.tin`): on one core and on two, 1200 keep-alive requests interleave routes whose middleware and handlers wait, and every answer must carry its own path parameter and middleware trace; waits in a routed handler or middleware overlap; 404, 405 with `Allow`, HEAD, bodies, a catch-all and pipelined order go through the router; and 20 WebSocket connections are accepted by a routed handler. A tick and relay handlers that panic (edition 1 fixture `guards.tin`, #230) run their deferred calls and are logged, and the core keeps ticking, handles the other messages and serves requests. The router's matching rules and errors are in `tests/v2/router.tin` and `router*_bad.tin`.
- Runtime lifetimes (`lifetime_check.py`): overlapping formatting on one core, deadlines for running and queued helper jobs, safe late read/write completion after task reuse, per-message WebSocket pool bounds, fragmented/control traffic, retained `Read` results, and automatic buffer cleanup after 300 connection cycles. Private probes are injected into temporary library copies.
- Structured concurrency (`scope_check.py`, Tin 1 #232, edition 1 fixture `scopes.tin`): `fetchAll`'s four children are all waiting at once inside a request (they count themselves, so a slow runner cannot fake or hide the overlap); a child fault cancels siblings that would otherwise wait 5 s and is the scope's fault; 60 concurrent requests with scopes on one core all get their own results.
- Guards (`guard_check.py`, #142, edition 1 fixture `guard_cleanup.tin`): a resource-cleanup callback registered inside a `guard` (through a probe in a temporary copy of `lib/tide`) runs, after the guarded call's defers, before the guard's value is the `fault.Panic` fault; one registered before the guard waits for its task's end.
- Boundary cancellation (`cancel_check.py`, Tin 1 #231): a cancel wakes a task parked in each client (`tide`, `wire`, `redis`, `mysql` including a pool wait, `postgres`, `websocket`, a helper-thread file read) within milliseconds with `canceled: <reason>`; cancelling one request or a block inside it never reaches a sibling or the parent; a block's earlier deadline gives `deadline exceeded`; a `limit memory` block in a handler (edition 1 fixture `limits.tin`, #235) past its budget gives the handler `fault.LimitExceeded`, also with 18 such blocks waiting on one core at once, and the server keeps serving; at the end of the grace period after SIGTERM, waiting requests end with `canceled: draining` and the process exits 0.
- Memory bounds (`memory_bounds_check.py`, #356, edition 1 fixture `memory_bounds.tin`): `anvil.Load`'s `Ingot` grows by what a handler keeps and its `Pool` by what a waiting request holds; past `TIN_MEMORY_SOFT` new requests get 503 with `Retry-After` and `on server.overload` runs, and once the holding requests end requests are served and `on server.recovered` runs. On Linux (macOS with `TIN_DOCKER=1`) the fixture also runs in a 256 MiB cgroup (a Docker container built `FROM scratch`) with neither variable set: a handler filling memory without bound ends at the default request budget with 500 and the server goes on, and keeping 4 MiB per request is refused with 503 by the default soft limit (after 192 to 232 MiB) while the process lives (with both bounds off, the same container is killed by the cgroup).
- Streaming responses (`stream_check.py`, #350, fixture `tools/ci/fixtures/stream.tin` and `examples/sse.tin`): raw-socket clients check the framing of server-sent events (the first event is out before the stream ends; keep-alive and a pipelined request behind a stream), eight 100000-byte chunks in order, HEAD, HTTP/1.0 up to the close, `Text` and `Flush`, an unsent stream, `Length` bodies, a short body and a panic (the connection closes, no error page follows), `Abort`, `SendFile` (a whole file, a range, 24 MiB in order, inside chunks, a missing file, a client that stops reading), a client that stops reading (the write timeout ends the stream), `Closed`, a stream longer than the request deadline that keeps writing, and the memory of a streamed response (1 GiB on Linux, 256 MiB on macOS: the server's RSS stays flat).
- Server lifecycle (`lifecycle_check.py`, Tin 1 #238, edition 1 fixture `lifecycle.tin`): a fault in `on app.start` or in a package-level `use` ends startup with status 1 before anything is accepted; after SIGTERM or `anvil.Drain(d)`, a waiting request ends with `canceled: draining` at the end of the grace period, both cores run `on core.stop` and close their `use`, then `on app.stop` runs (its own waits work) and the process exits 0.
- Client address (`lifecycle_check.py` `client_addr`, #355, fixture `tools/ci/fixtures/client_addr.tin`): `RemoteAddr` is the client socket's own address; `ClientIP` ignores `X-Forwarded-For` and `Forwarded` from an untrusted peer and takes the rightmost untrusted address from a trusted one (IPv4, IPv6 per RFC 5952, mapped IPv4, quoted `for=` with ports, malformed entries); a bad network is refused at startup; and the access log of the anvil docs, a herald line per request, carries each request's `client`. `replay_check.py` adds the peer to the capsule (schema 2, read back with Python's `hmac`) and replays it: a replayed request sees the recorded `RemoteAddr` and `ClientIP` (IPv4, IPv6, trusted and untrusted), a schema 1 capsule and a malformed peer answer "", and schema 3 is refused.
- Clients and protocols, each against a small server written in Python inside the check, so no service has to be installed: `redis_check.py` (concurrent load, command batching, deadlines that keep replies in step, reconnects, AUTH), `mysql_check.py` (bound values, pool waits, deadlines, both auth plugins including the RSA exchange, wrong passwords, reconnects, and the process-wide cap of #359: with `TIN_CORES=8` and `MaxTotal` 6 the server never sees more than 6 connections (a close the server has not noticed yet may add one or two) while 48 concurrent statements and 32 sequential ones across the cores all succeed, and the `Pool` default gives 2 x 32 connections on two cores and 32 x 2 on thirty-two, counted by the fake server or, against a real MySQL, through `information_schema.PROCESSLIST`), `postgres_check.py` (SCRAM/MD5/cleartext, Unicode passwords, typed binary parameters, OID results, statement cache eviction, transactions, pool waits, deadlines, malformed frames, 1000 inserts, and the same process-wide cap and `Pool` default checks, counted through `pg_stat_activity` against a real server) and `websocket_check.py` (RFC 6455 rules, 300 idle connections and 20 concurrent streams on one core, the Tin client). Each of the three also runs a second time over TLS 1.3 (#124): the fake server behind Python's `ssl` module with a certificate made for the run, the client on `rediss://`, SSLRequest (MySQL, where full `caching_sha2_password` authentication sends the password without RSA) and `sslmode=require` (PostgreSQL, which also checks that `require`, `verify-full` and unknown modes never fall back to plain TCP). On `ubuntu-24.04` the MySQL check also runs against the runner's own MySQL 8 and the PostgreSQL check runs against its preinstalled PostgreSQL with a SCRAM user, each in the clear and over TLS (the servers' own certificates; verification arrives with X.509 support); `REDIS_ADDR` / `MYSQL_ADDR` / `POSTGRES_ADDR` point the checks at real servers locally.
- Deadlines in a database call (`mysql_check.py`, Tin 1 #233, edition 1 fixture `mysql_within.tin`): a 3 s statement inside `within 50ms`, and inside `within 10s` nested in `within 50ms`, fails with `fault.DeadlineExceeded` after about 50 ms and the next statement of the request succeeds; `task.Deadline()` in a request reads `TIN_DEADLINE_MS`.
- Cryptographic primitives (`crypto_check.py`, #124): `seal`'s SHA-2 hashes, HMAC, HKDF, P-256 ECDH (including invalid-curve points and compressed keys), X25519 (low-order points must fail), AES-128/192/256-GCM and ChaCha20-Poly1305 (every changed tag, ciphertext or nonce length must fail) against the Wycheproof files in `tests/wycheproof/` (pinned, including the invalid inputs, which must be rejected) and against Python's `hashlib`/`hmac` on every message length across the padding boundaries and random inputs. The fixture `tools/ci/fixtures/crypto_vectors.tin` reads one vector per line on stdin. Every vector runs twice: on the CPU's AES instructions where the runner has them, and on the constant-time software path (`TIN_SEAL_SOFT=1`). `test_crypto_generated.py` checks that `lib/seal/aes_sbox.tin` and `selfhost/aes_hw.tin` match their generators.
- TLS 1.3 client (`tls_check.py`, #124): the RFC 8448 §3 trace through the real client (a private probe in a copy of `lib/tls` plays the trace's server: both Finished messages, application data, a NewSessionTicket, KeyUpdate both ways, close_notify, and a changed byte giving an encrypted `bad_record_mac`); `openssl s_server -tls1_3` with RSA, ECDSA and Ed25519 certificates, every cipher suite, X25519 and P-256 (by HelloRetryRequest), ALPN, server KeyUpdates with and without request_update, and a TLS 1.2-only server refused (where the runner has OpenSSL 3); Python `ssl` servers for a handshake timeout, a non-TLS server, truncation without close_notify, verification on by default, `wire` over `https://` and `websocket` over `wss://`; and on one core eight request handshakes that each take 0.5 s overlap, a fast request is not delayed, and the request deadline ends a handshake that never completes. Certificates are generated per run.
- Certificates and signatures (`x509_check.py`, #124 phase 2): a fresh test PKI per run (`bench/ref/x509_pki`: root, intermediates and leaves, and each bad case: expired and not-yet-valid certificates, wrong host names, untrusted roots, missing intermediates, bad signatures, non-CA intermediates, SHA-1, RSA-1024, over-long chains, path lengths, key usages, name constraints, unhandled critical extensions) verified by `tests/v2/seal_x509.tin` and by Go's `crypto/x509` (`bench/ref/seal_x509`), both of which must give each case's expected outcome; ECDSA chains (P-256 and P-384), Ed25519 chains and TLS signatures; the checked-in PKI, certificate fields and the Wycheproof RSA, ECDSA and Ed25519 files (`tests/wycheproof/rsa`, `ecdsa`, `ed25519`) give Go's results; every byte of every PKI and system root certificate is flipped three ways and Tin must reject each mutant Go rejects; private keys (PKCS #8, PKCS #1, SEC 1) and signatures from the test keys in `tests/data/keys` equal Go's where deterministic (PKCS #1 v1.5, RFC 6979 ECDSA) and verify in Go where random (RSA-PSS); `seal.SystemRoots` parses the certificates of the system bundle that Go parses.
- The v0.4 service benchmark (`.github/workflows/bench.yml`) is separate and runs only on demand: Redis and MySQL service containers, wrk2 built from source, Tin vs Go + chi. It is never a merge gate.
- Linux benchmarks (`.github/workflows/bench-linux.yml`): the CPU suite (`bench/v2`) and the HTTP suite (`bench/http/run_wrk.sh`) on `ubuntu-24.04` and `ubuntu-24.04-arm`, weekly and on demand (Actions, Run workflow); it does not run on pull requests. Each job keeps Tin/Go reference measurements and compares the selected revision against its base using matching compiler/library trees. Reference performance is Linux only; macOS is a development platform (docs/PERFORMANCE.md, "Benchmark policy"). Output mismatches, crashes, timeouts and failed HTTP measurements fail the workflow; timing thresholds flag review and never act as an automatic merge gate. Raw JSON samples and HTTP logs are retained.
- Harness self-tests ensure expected output cannot disguise crashes/timeouts or unexpectedly accepted negative programs. Benchmark self-tests check alternating medians, output equality on every repetition, matching revision library trees, and failed measurements.

The Python harness uses only the standard library. Shell entrypoints now require Python 3. Native runtime probes have a 20-second timeout, core dumps disabled, and a 512 MiB virtual-memory limit on Linux. The first-allocation crash reproducer is Linux-only: macOS can map writable memory beyond the undersized allocation, making a SIGSEGV expectation unreliable there. HTTP tests require `ps` (available on hosted Ubuntu).

Linux amd64 is a supported execution gate: the `ubuntu-24.04` job builds the compiler from `seed/tinc-linux-amd64`, checks the self-hosting fixed point and runs every suite natively on x86-64 hardware. Refresh that seed with `make linux-amd64-bootstrap` (emulated container on an arm64 Mac).

## Existing defects versus new regressions

The initial baseline contains explicit `known_failure` contracts for open issues #1–6. These are visible as **XFAIL**, not PASS, in logs, JSON artifacts and the Actions summary. A known failure matches its phase, exit code and specified output/diagnostic; unrelated failures are not exempt. A timeout is never an expected failure.

If a fix makes the expected behavior pass while the exemption still exists, CI reports **XPASS and fails**. Keep the test and remove its `known_failure` field in the same fixing PR. Thereafter a recurrence is a normal blocking failure. Do not delete the test or weaken the expected contract to close an issue. New failures must not be added to the exemption list just to unblock a PR.

The issue audit checks GitHub for every exempted issue. Closing an issue while an exemption remains fails the audit. It runs on pushes/PRs and on issue close/reopen events against the default branch. It reads issue state only; it does not execute issue text, edit workflow code, comment, reopen issues or auto-merge changes. If closing as a duplicate or not planned, explicitly review and explain any corresponding coverage change.

## Resolving an issue

1. Add a small deterministic reproducer and the intended correct behavior. For a language/runtime bug, use `tests/regressions/NAME.tin` and an entry in `cases.json` with the issue number. Every `.tin` file must have exactly one entry; the runner discovers new cases without workflow edits. A request recorded in production becomes such a case with `tin replay CAPSULE --against FIXED.tin --save-test NAME --issue N` (docs/TOOLING.md §8.1, #242): the case names its capsule and the public key it is sealed under, and the runner replays it.
2. Implement the fix. If the case already exists, remove its `known_failure` contract and keep its expected behavior. For non-Tin tooling bugs, extend `tools/ci/test_*.py`; unittest discovers them automatically. Issues #7 and #8 are covered by these harness tests.
3. Run the commands below and include the regression test names in the PR. Expand the workflow only when the issue needs a new environment/tool, such as native amd64 or cgroup namespace fixtures.
4. Let CI pass and merge the PR before closing the issue (a `Fixes #N` PR reference closes it on merge).

This avoids a bot rewriting Actions after closure: the regression becomes required **in the fixing PR**, before its code can merge. The issue audit catches forgotten exemptions afterward.

`tools/linuxtest.sh` and `tools/x64fuzz/linuxtest_amd64.sh` use the same strict runner for Docker cross-tests. They check negative diagnostics on the build host and positive outputs/exit codes in the chosen image. `TIN_LINUX_IMAGE` chooses the image; `TIN_ROOT` can select a library tree. The old `X64_TEST_DIR` output option is replaced by unique temporary directories and logs under `bin/ci/`.

Diagnostics are uploaded for 14 days even if a job fails. No compiled output is cached: a stale compiler or test binary cannot make a fresh checkout pass.

PostgreSQL checks use a private users table in the selected database; choose a throwaway
instance/database for local real-server checks. They exercise `examples/postgres.tin`
with extra test routes compiled only into the fixture service. No downloads are needed
for the fake checks. The native Ubuntu x86-64 CI job starts the runner's PostgreSQL and
creates a dedicated `tin` database/user with a SCRAM verifier; it does not install packages.
`POSTGRES_TIMEOUT_MS` configures the example's operation timeout independently of
`TIN_DEADLINE_MS`. The crypto suite checks published PBKDF2/RFC 1321 vectors and Unicode
normalization/bidirectional/prohibited-input cases; `tools/gen_saslprep.py` regenerates
fixed Unicode 3.2 tables with Python's standard library.
